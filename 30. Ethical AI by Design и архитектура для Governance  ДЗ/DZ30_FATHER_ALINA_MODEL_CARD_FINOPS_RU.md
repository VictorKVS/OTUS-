# Часть 1. Governance — Model Card

## 1. Основные сведения

| Поле | Описание |
|---|---|
| Объект документа | **Model/System Card для конфигурации** FATHER/ALINA Knowledge Assistant: генеративная модель + retrieval + проверка доказательств + policy gate |
| Назначение | Объяснять материалы и готовить ответы со ссылками на разрешённые первоисточники; помогать с учебными и техническими вопросами |
| Вид модели | Генеративная LLM как компонент RAG-системы; модель может быть заменена адаптером |
| Базовая модель | Точный provider/model/version/hash подлежит фиксации в runtime-манифесте. **Не подтверждён в материалах к этому ДЗ** |
| Тип данных | Документы/учебники/технические материалы, извлечённые фрагменты, пользовательский запрос, журналы происхождения |
| Владелец | Ответственный за FATHER/ALINA; конкретное лицо/контакт назначаются перед внедрением |
| Статус | Проект/лаборатория; production approval: **НЕ ВЫДАНО** |
| Лицензия | Лицензии базовой модели и каждого корпуса должны быть проверены до публикации/эксплуатации |

**Важное различие:** оригинальная Model Card описывает конкретную версию модели. Здесь дополнительно описана система RAG, поскольку качество, риски и происхождение ответа зависят не только от весов LLM. Для промышленной эксплуатации необходимы две связанные записи: `Foundation Model Card` (для точной версии/поставщика) и `Application/System Card` (для FATHER/ALINA pipeline).

## 2. Intended Use & Limitations

**Предусмотренное использование:**
1. учебные ответы и объяснения с прослеживаемыми источниками;
2. анализ технической документации в разрешённой области;
3. подготовка предварительных структурированных заметок и рекомендаций для проверки человеком;
4. помощь с навигацией по базе знаний и сравнением фрагментов.

**Непредусмотренное/запрещённое без отдельной квалификации:**
- самостоятельные медицинские, юридические, кадровые или финансовые решения, влияющие на человека;
- оценка учеников, работников или групп людей по чувствительным признакам;
- публикация персональных/закрытых документов без прав;
- автоматический запуск привилегированных инструментов по тексту LLM;
- утверждение о достоверности без первоисточника либо о проведённом испытании без evidence.

**Ограничения:** генерация правдоподобных, но ложных ответов; неполнота индекса; устаревание документов; ошибки OCR; межъязыковые различия; prompt injection в retrieved content; различие поведения версий моделей; неустойчивые ответы при неоднозначном запросе.

## 3. Данные и возможная предвзятость (Bias analysis)

**Предобучение foundation model:** состав и доли источников **не установлены по предоставленным материалам**; нельзя утверждать, что конкретный сторонний датасет использовался. До выпуска нужны официальный Model Card поставщика, версия, лицензия, доступное описание обучения и известные ограничения.

**Данные FATHER/ALINA RAG:** проектно — разрешённые книги, учебные материалы, документация и стандарты; фактический индекс, права, даты индексации, языки, лицензии и версии требуют инвентаризации. Retrieval **не является дообучением весов**: данные поиска нельзя называть обучающим датасетом LLM.

**Систематические смещения и риски:**
- преимущество хорошо оцифрованных и популярных источников над редкими;
- русско-английское неравенство качества поиска/ответов;
- неравномерная представленность областей и терминологии;
- устаревшие нормы и документы могут попасть в ответ;
- неодинаковая точность для разных форматов (PDF/DOCX/OCR) и трудности запросов;
- ответы могут имитировать авторитет при недостаточном evidence.

**Снижение:** карта источников и лицензий; версионирование; дедупликация и контроль качества парсинга; balanced test set по языкам/типам документов/сложности; показывать цитаты; `INSUFFICIENT_EVIDENCE` вместо догадки; контроль запроса на доступ.

## 4. Fairness — метрики и golden dataset

В учебном поисковом ассистенте оценка демографических групп **не является автоматически обоснованной**. Предлагается тестировать равномерность **качества обслуживания** между релевантными группами использования: язык RU/EN, тип документа, сложность задачи, предметная область, способ извлечения OCR/текст.

| Показатель | Определение / смысл | Статус |
|---|---|---|
| Grounded Answer Rate | Доля ответов, у которых ключевые утверждения подтверждены источником | Требует измерения |
| Citation Precision | Доля приведённых ссылок, действительно подтверждающих связанное утверждение | Требует измерения |
| Unsupported Claim Rate | Доля ответов с неподтверждённым существенным утверждением | Требует измерения |
| Abstention Appropriateness | Доля корректных отказов при нехватке данных; отдельно ложные отказы | Требует измерения |
| Error Rate by Slice | Доля ошибок отдельно по RU/EN, OCR/тексту, предметным областям | Требует измерения |
| Max Slice Disparity | Разница между худшим и лучшим качеством по релевантным срезам с доверительными интервалами | Требует измерения |

**Golden dataset (план):** минимум 4 категории вопросов (фактические, многодокументные, неоднозначные, невозможные), каждый в RU/EN там, где правомерен перевод, с примерами PDF-text и OCR. Эксперты размечают эталон, допустимые источники, нужное поведение отказа и критичность ошибки; тестовый корпус фиксируется по версии/хешу, не пересекается с материалом адаптации промптов. Размер выборки и статистическая мощность задаются после пилотного исследования, а не придумываются.

**Критерий выпуска (предлагаемый, не измеренный):** отсутствуют критические неподтверждённые решения, выполнены согласованные пороги precision/groundedness, нет необъяснённого значимого разрыва между срезами; отдельно проверены опасные сценарии. Точные пороги согласует владелец риска.

## 5. Accountability, Transparency и Decision Audit Log

```text
User Request
   -> Authentication/Authorization & PII policy
   -> Query Router
   -> ALINA Retrieval [source IDs/version/hash]
   -> Model Adapter [model ID/version + prompt/policy version]
   -> Evidence Verifier + Guardrails
   -> Human Review (для чувствительных/высокорисковых решений)
   -> Answer / Clarification / Safe refusal
                       |
             Decision Audit Event
                       |
    Access-controlled append-only / tamper-evident storage
                       |
             Reports, alerts, incident review
```

**Минимальные поля Decision Audit Event:** `event_id`, время UTC, `request_id`, псевдонимизированный subject/tenant, purpose, разрешённая роль, маршрут, версия модели и промпта, ID/версии документов и цитат, outcome/status, evidence_verification, safety_flags, human_review_decision, длительность, токены/оценка цены, версия политики, trace ID.

**Privacy by design:** не складывать в журнал необработанные запросы, полные тексты, секреты и персональные данные по умолчанию; применять маскирование, сроки хранения по классификации, RBAC, шифрование, контроль доступа, WORM/append-only там, где требуется. Хеш записи помогает обнаруживать изменения, но сам по себе не делает журнал неизменяемым.

**Governance gates:** `DATA_APPROVED → MODEL_VERSIONED → EVALUATED → SECURITY_REVIEWED → COST_REVIEWED → HUMAN_APPROVED → RELEASED`. Без evidence выпуск блокируется. Откат по `model_version`/`retrieval_index_version`/`prompt_version`.

**Роли:** владелец продукта (intended use), владелец модели (карточка/версии), владелец данных (лицензии/права), ИБ (риск/аудит), FinOps (счёт/затраты), независимый экзаменатор POLYGON (тесты), ответственный человек (release decision). Роли проектные, не заявлены фактически назначенными.

# Часть 2. FinOps — анализ счёта +50%

## 6. Исходные допущения и структура счёта

**Сценарий:** ежемесячный бюджет **100 000 ₽**, фактический условный счёт **150 000 ₽**, отклонение **+50 000 ₽ / +50%**. Ниже не фактические биллинговые данные и не подтверждённые тарифы провайдера.

| Статья | Бюджет, ₽ | Факт, ₽ | Отклонение, ₽ | Вероятная причина (гипотеза) |
|---|---:|---:|---:|---|
| GPU instances | 40 000 | 70 000 | +30 000 | Забытые тестовые GPU, отсутствие schedule/autoscaling |
| LLM inference / API | 25 000 | 35 000 | +10 000 | Избыточная модель, повторные запросы, длинные контексты |
| Logs & observability | 10 000 | 20 000 | +10 000 | Избыточное логирование, долгий hot retention, high-cardinality |
| Storage / backups | 15 000 | 15 000 | 0 | Нет исходных признаков перерасхода |
| Network / data transfer | 10 000 | 10 000 | 0 | Нет исходных признаков перерасхода |
| **Итого** | **100 000** | **150 000** | **+50 000** | **+50%** |

**Порядок диагностики:** (1) сравнение invoice по дням, SKU, среде, проекту, тэгам, GPU-hours и token usage; (2) сверка ресурсного inventory с расписаниями и владельцами; (3) атрибуция по model/tenant/request; (4) аномалии retention/trace cardinality; (5) связь затрат с successful outcomes и качеством. Приведённые причины — гипотезы до сверки детализации счёта.

## 7. Технический Cost Optimization Plan

| Мера | Механизм и ограничения | Предполагаемая экономия в мес. | Как проверить |
|---|---|---:|---|
| GPU idle shutdown/rightsizing | Автоостановка dev/test; планирование GPU, scale-to-zero в совместимых workloads; Spot только для прерываемых фоновых задач | 25 000 ₽ | GPU-hours, utilisation, отказоустойчивость |
| Model routing + caching + batching | Простые задачи на меньшую модель/детерминированные функции; RAG context trimming; кэш без утечек tenants | 10 000 ₽ | goldenset quality, p95, cache precision, tokens/success |
| Logs TTL + tiers + sampling | Структурированные события, ограничение hot-retention и debug sampling; **аудитные записи хранить по утверждённой политике** | 8 000 ₽ | GB-day, audit completeness, recovery and investigations |
| Storage cleanup / lifecycle | Удаление подтверждённых дубликатов, tiering, lifecycle по метаданным, без разрушения backup | 3 000 ₽ | inventory, restore test, storage GB-month |
| **Этап 1: возможное снижение** | **Не гарантировано до измерения** | **46 000 ₽** | **150 000 → 104 000 ₽/мес.** |
| Additional GPU optimization | Ещё 5 000 ₽ при доступном workload и подтверждённом качестве/SLO | 5 000 ₽ | workload test + comparison |
| **Этап 2: сценарная цель** | **Не гарантирована** | **51 000 ₽** | **150 000 → 99 000 ₽/мес.** |

**Model Distillation:** рассматривается как долгосрочная опция с затратами на подготовку данных, обучение, проверку качества, безопасность, лицензию и окупаемость. **Не включена** в обещанную экономию до эксперимента.  
**Spot:** не применять для невосстанавливаемых критических запросов; требуются checkpoint/retry, budget gates и отказоустойчивость.  
**TTL:** применять только к допустимым диагностическим и временным данным; не удалять аудиторские записи вопреки требованиям хранения.

## 8. План действий и контроль

| Срок | Мера | Ответственный по роли | Подтверждение |
|---|---|---|---|
| 0–2 дня | Разобрать счёт и включить alerts/tags по product/env/model | FinOps + Platform | Billing export, anomaly report |
| 3–7 дней | Остановить idle GPU; настроить schedule; отделить dev/stage/prod | Platform/SRE | GPU-hours baseline vs after |
| 1–2 недели | Routing, cache и context policies на test environment | AI Engineering | quality and latency benchmark |
| 1–2 недели | Retention, hot/cold storage и audit protection | Observability + Security | storage trend, audit completeness |
| 2–4 недели | Spot/batching/distillation feasibility + architecture ADR | AI Architect + Product | impact/cost/risk and rollback |
| Каждый месяц | Review cost / successful qualified answer, budget vs actual | Product + Finance + Engineering | FinOps dashboard, signed decisions |

**Stop criteria:** rollback при падении качества ниже согласованного baseline, ухудшении SLO, повреждении evidence/logs, нарушении требований ИБ/данных. Экономия не должна достигаться ценой вреда пользователю или недоказанных ответов.

## 9. Экономика + качество: как выбирать решение

Оцениваются не только `cost/request` и `cost/1k tokens`, но и `cost/qualified_answer = total_cost / number_of_answers_passing_evidence_and_quality_tests`. В сравнении альтернатив фиксируются: качество по релевантным срезам, галлюцинации, latency, безопасность, доступность, нагрузка, стабильность и затраты на изменение.

**Пример:** дешёвая модель снижает цену каждого вызова, но если увеличивается доля ошибок и повторных обращений, стоимость одного проверенного ответа может вырасти. Поэтому выбранная мера внедряется только после A/B на фиксированном тестовом корпусе и с откатом.

## 10. Вывод и решение архитектора

Предлагается **не выпускать** FATHER/ALINA как автономную high-impact decision system без разрешённого сценария, документированных источников/моделей, golden dataset, воспроизводимого fairness/quality review и контроля полномочий. Для учебной RAG-системы предлагается staged rollout с human oversight и Decision Audit Log.

По учебному сценарию перерасход 50% объясняется в первую очередь GPU-hours, LLM usage и observability. При благоприятном подтверждении предложенная оптимизация даёт **сценарную** экономию 51 000 ₽/мес. и бюджет 99 000 ₽/мес.; никакая экономия не объявляется достигнутой без измерения.
