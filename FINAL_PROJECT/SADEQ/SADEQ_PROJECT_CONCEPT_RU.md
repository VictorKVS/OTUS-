# SADEQ — Software & Agent Design, Engineering & Qualification
**Универсальная инженерная платформа проектирования, разработки, тестирования и квалификации ПО и интеллектуальных агентов.**

**Класс документа:** концепция / IDEA+; **статус:** PROJECT PROPOSAL, NOT IMPLEMENTED, NOT QUALIFIED.
**Назначение:** автономная (on-prem / air-gapped) система полного инженерного цикла, позволяющая создавать разные специализации интеллектуальных агентов на едином проверенном ядре без копирования программной логики.

## Публичное позиционирование
**SADEQ — от идеи и архитектуры до доказанно работающего программного продукта.**

## Сквозная производственная линия
`IDEA+ → REQUIREMENTS → ARCHITECTURE → ALGORITHMS → API CONTRACTS → DEVELOPMENT → VERIFICATION → QUALIFICATION → RELEASE → FEEDBACK`

**Интеллектуальная линия:** `INGEST → KNOWLEDGE → STATE / EVENT → ANALYSIS / FORECAST → APPROVED ACTION → FEEDBACK`.

**Профиль специализации:** `mission, inputs, ontology, knowledge, algorithms, tools, permissions, autonomy, expected_outputs, evaluation_suite, budgets`. Новая специализация не объявляется готовой, пока независимая квалификация не подтверждает соответствие контрактам.

## Выпускной проект: обязательная архитектура
C4 Context, Container, Component, Code (для критических модулей); Deployment (DMZ, GPU, secrets, балансировка); Sequence (guardrails, GraphRAG, agent loop, tool policy, response); ER (documents, chunks, graph nodes/edges, ACL, history, audit); ADR (trade-offs). Control Plane отдельно от Data Plane. Локальный inference, LangGraph/state machine, Qdrant + graph database, OpenTelemetry/Prometheus. Offline deny-all egress и отрицательный тест User B → защищённые данные обязательны.

## Масштабирование и финансовые следствия
| Переход | Как масштабируем | Первоначальная стоимость | Постоянная стоимость | Порог перехода |
|---|---|---|---|---|
| 0→1 MVP | Одна машина, локальная LLM, GraphRAG | инженерные часы, настройка, оборудование | электроэнергия, обслуживание | доказанный результат end-to-end |
| 1→3 специализации | Подключаем онтологии, алгоритмы и инструменты | доменные контракты и тесты | сопровождение источников, тестов | три независимые квалификации |
| 3→20 конфигураций | Реестр и декларативная фабрика | автоматизация фабрики | регрессия, контроль версий | измерена экономия времени на новую специализацию |
| Рост запросов | очередь, batching/cache, модельный router, затем GPU pool | новые GPU, storage, сеть | энергия, резерв, эксплуатация | p95/TTFT/throughput нарушают SLO |
| Рост данных | разделение индексов и графов, backup | диски и миграции | индексирование, хранилище, архив | реальный рост корпуса/retention |
| Рост критичности | изолированные контуры, HA/DR | серверы и резервные площадки | дублирование ресурсов, операции | подтверждённые требования RTO/RPO |
| Продажа заказчикам | tenancy, установщик, поддержка и аудит | hardening, документация, юридические затраты | customer success, обновления, поддержка | cost per qualified outcome и маржинальность |

### Иллюстративная модель разработки — не коммерческая смета
- Общее ядро и фабрика: **600 инженерных часов**.
- Отдельный агент без общей платформы: **200 часов**.
- Новая специализация поверх платформы: **40 часов**.
- При N агентах: `standalone=200×N`; `platform=600+40×N`.
- Первая экономия начинается при **N=4** (760 против 800 часов).
- Для 20: 1 400 против 4 000 часов; условная экономия 2 600 часов **только если все 20 задач сопоставимы и одинаково квалифицированы**.
- Добавить к смете: CAPEX GPU, электричество, backup, персонал, лицензии, адаптеры, безопасность, стоимость предметной экспертизы и независимой проверки.
- Ключевая метрика: `cost_per_qualified_outcome = total_cost / independently_accepted_results`.

## Quality Gate и доказательства
Нужны: проверка лицензий и воспроизводимости, реальный GraphRAG, отсутствие внешнего трафика, контроль прав на все пути retrieval, результаты unit/integration/security/black-box тестов, замеры RPS/p95/TTFT/tokens/s, provenance и ревизии. **Ни один статус READY не ставится на основании одной диаграммы или демо.**

## Правила публичного использования
- Названия компонентов исключительно функциональные; нейтральные папки, заголовки, логотипы.
- Никаких ссылок на внутренние репозитории, личные пути, авторские обозначения, уникальные кодовые имена в публичной презентации.
- Для настоящего разделения публичной и внутренней идентичности требуется отдельный репозиторий и проверка метаданных, истории Git, автора коммитов и зависимостей. Один только нейтральный текст не создаёт анонимности.
