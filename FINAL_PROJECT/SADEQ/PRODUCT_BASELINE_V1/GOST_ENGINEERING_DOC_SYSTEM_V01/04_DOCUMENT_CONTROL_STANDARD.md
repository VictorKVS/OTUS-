## Обозначения
- `DOC, REQ, FR, NFR, BUS, THR, ALG, CMP, FLOW, CT, ADR, TEST, EVI, REL` — уникальные **внутренние ключи трассировки**, не замена нормативному шифру документа.
- Поле `normative_designation` добавляется только после выбора применимого стандарта и проекта/изделия и сверки с заказчиком.
- Одно содержание не должно получать два действующих взаимоисключающих нормативных статуса.

## Контрольный лист (общие правила)
1. Титульный лист с наименованием изделия/АС и документа, согласованием, версия/дата, применимостью.
2. Ведомость и содержание с номерами разделов/страниц, лист регистрации изменений.
3. Нормативные ссылки и их редакции/поправки, терминология/сокращения, область действия.
4. Однозначные требования с ID, параметрами, единицами, критериями и методами проверки.
5. Схемы с названием, номером, легендой, источником диаграммы и ссылкой на элемент/поток.
6. Для кода: кодировка, язык, зафиксированные зависимости, source hash, SBOM и лицензии.
7. Для сведений ИБ: класс информации, минимизация, допуски, безопасные публикации, redaction.
8. Решение о подписании/утверждении отдельно от Git commit; Git может доказывать provenance, но не полномочие подписанта.
9. PDF/DOCX — выпуски; Markdown/YAML/OpenAPI/Mermaid — управляемые исходники, не автоматически ГОСТ-формат.
10. На каждом переходе: полнота, согласованность, proof of tests, независимое review, applicability and contract-specific template validation.

## Иерархия истин
1. Договор/утверждённое ТЗ/применимые НПА и стандарты.
2. Утверждённая базовая версия проекта и сведения о конфигурации.
3. Подписанный документ с реквизитами и ссылкой на исходники.
4. Исходный Markdown/YAML/дизайн до утверждения.
5. Презентация — производная иллюстрация без самостоятельных новых утверждений.

## Режим информации
Не создавать в публичном GitHub реальные сведения ограниченного доступа, чувствительные схемы боевого применения, ключи и персональные данные. При специальном договоре должны быть отдельно оформлены матрица допусков, список разрешённых инструментов, правила репозитория, обмена и хранения.

## Политика визуализаций
C4 — архитектурные уровни; BPMN — бизнес-процесс; UML/DMN — взаимодействия и решения; ГОСТ 19.701 — нормативно выполненные схемы алгоритмов; ER — модель данных. Mermaid исходник — удобен для разработки, но ГОСТ-совместимую версию выпускают отдельной проверенной диаграммой. Инвесторская презентация берёт утверждённые показатели, маркирует сценарные оценки.
