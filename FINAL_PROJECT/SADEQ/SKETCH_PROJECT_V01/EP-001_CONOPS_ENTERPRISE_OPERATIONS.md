# ЭП-001 — Concept of Operations / Концепция эксплуатации
**ID:** SADEQ-EP-001 · **Версия:** 0.1 · **Статус:** DESIGN / NOT IMPLEMENTED / NOT APPROVED.

## 1. Бизнес-заказ: предмет автоматизации
Целевое место: корпоративная ИТ-служба (Service Desk L1/L2) организации с внутренним серверным контуром. Конкретная компания не определена. SADEQ **не заменяет** ITSM, инженера, владельца сервиса или уполномоченного согласующего; он ускоряет поиск материалов и подготовку обоснованного предложения с проверяемой историей. В лаборатории используется **искусственный контур** заявок `INC-001` и нормативной базы без персональных данных.

### Акторы и RACI проекта
| Роль | Задача | Что может / чего не может |
|---|---|---|
| Оператор L1/L2 | создаёт/исследует инцидент; читает evidence | может предложить действие, не назначает себе расширенные права |
| Data Owner | утверждает источники и их использование | контролирует scope, редакции, retention |
| Service Owner | устанавливает бизнес-правила и приоритет | несёт ответственность за решение об изменении |
| Approver | утверждает точный ActionProposal | согласует версию/срок/объект; не утверждает самопроизвольный другой tool call |
| Security Officer | утверждает модель угроз и policy | независим от LLM и владельца prompt |
| Platform Operator | устанавливает/наблюдает/откатывает версию | не обходит human release policy |
| POLYGON Examiner | проводит независимые тесты кандидата | не изменяет исходники кандидата и правила теста |
| SADEQ runtime | ищет и анализирует, формирует ActionProposal | не может сам себе выдать право или подтвердить собственный выпуск |

## 2. Физический горизонт, не фиктивное продуктивное размещение
**LAB P0:** Win11+WSL2/Docker, локальная RTX3060 12 GB, RAM 32 GB, API, PostgreSQL, Qdrant, Ollama, mock ITSM, изолированный тестовый контур, зафиксированный набор синтетических материалов. Подбор конкретных моделей, VRAM/latency — после теста.
**CORPORATE PILOT:** внутренний серверный сегмент, IAM/SSO, source registry, разделённые credential boundaries, разрешённые корпоративные документы и тестовая ITSM, security review. Отдельный документ разрешения заказчика обязателен.
**PROD:** только после оценки рисков, BIA, backup/restore, испытаний, приёмки заказчиком и эксплуатационного решения.

## 3. Один воспроизводимый бизнес-день
**08:55.** Оператор открывает очередь заявок в браузере.
**09:00.** Входящий `INC-001`: «Сервис X недоступен», подтверждённый tenant/identity, описан объект `SVC-X`. Данные демонстрационные.
**09:01.** ALG-01 проверяет отправителя и структуру; ALG-02 отсекает повтор; ALG-03 сопоставляет бизнес-объект; ALG-04/05 записывают событие и версию состояния; ALG-06 определяет необходимость обработки.
**09:02.** ALG-07 извлекает разрешённые SOP и известные случаи с chunk ID, версией и ссылкой; ALG-08 сопоставляет гипотезы, выводит несогласованности и условия ABSTAIN. Время — **иллюстративная последовательность**, а не SLO.
**09:03.** ALG-10 формирует только типизированное предложение `update_ticket_status`, evidence и expected postcondition; UAG ALG-11 проверяет ACL, tool scope, state version и срок согласования.
**09:04.** Approver принимает решение; при APPROVED UAG повторно проверяет action hash/state/TTL и передаёт вызов в mock ITSM.
**09:05.** ALG-12 самостоятельно читает authoritative record ITSM; фиксирует VERIFIED или MISMATCH. Результат и trace доступны аудитору. Указанное время **не фактическое измерение**.

## 4. Нормальные и отклоняющиеся маршруты
- Duplicate → возврат существующего event receipt, не повторный side effect.
- Unknown schema/nested property → REJECT before storage/tool.
- Ambiguous object identity → REVIEW_REQUIRED, нет silent merge.
- Недостаток источников/противоречие → ABSTAIN и человеческая оценка.
- Forecast невозможен → NOT_AVAILABLE, не блокировать P0.
- Prompt injection в документе → источник трактуется как данные, tool policy не изменяется.
- Неавторизованный tenant или stale approval → DENY, no execution.
- Timeout после отправки в ITSM → EXECUTION_UNKNOWN; проверить authoritative state, не выполнять слепой повтор.
- HTTP 200 но состояние не соответствует ожидаемому → MISMATCH/INCIDENT, не SUCCESS.
- Незакрытый критичный тест → NOT_QUALIFIED, блокировка выпуска.

## 5. Что знает агент и что выполняет программа
**Материалы:** MAT-01 каталог услуг/SLA, MAT-02 SOP, MAT-03 известные ошибки, MAT-04 synthetic tickets, MAT-05 объекты, MAT-06 mock ITSM OpenAPI, MAT-07 policies, MAT-08 закрытые схемы, MAT-09 goldens, MAT-10 attacks, MAT-11 события.
**Детерминированные ALG:** 01/02/03/04/05/06/10/11/12 — контракт, права, состояние, решение по правилам, execution verification. **LLM-assist:** 07 retrieval + 08 анализ гипотез; LLM не удостоверяет истинность источника и не выдаёт права. ALG-09 в P0 возвращает NOT_AVAILABLE при отсутствии серий.
**Не путать:** индексацию RAG и отладку prompt/workflow с изменением весов модели. Fine-tuning исключён P0.

## 6. Показатели проекта, без выдуманных эффектов
Измеряем по зафиксированному набору кейсов: verified outcome rate, citation support rate, retrieval Recall@k, unauthorized tool calls, cross-tenant disclosures, approval bypass, p95 latency, TTFT, VRAM, cost per verified outcome. Baseline: ручной сервис-деск сценарий и неагентный RAG в одинаковых условиях. Пороговые значения утверждают до acceptance test.
