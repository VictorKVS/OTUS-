# ТЕХНИЧЕСКОЕ ЗАДАНИЕ НА СОЗДАНИЕ АВТОМАТИЗИРОВАННОЙ СИСТЕМЫ
## SADEQ Enterprise Operations Copilot (SADEQ UAA)
**Внутреннее обозначение:** SADEQ-TZ-003; **редакция:** 0.3; **дата:** 2026-11-27.  
**Нормативная основа:** ГОСТ 34.602-2020; стадии ГОСТ Р 59793-2021; документация ГОСТ 34.201-2020.  
**Статус:** ПРОЕКТ ДЛЯ СОГЛАСОВАНИЯ — не утверждён заказчиком; правовой статус оборонного заказа/военной приёмки не установлен.  
**Заказчик:** не определён (учебно-исследовательский R&D); **Разработчик:** независимый проект FATHER/SADEQ; **Владелец технических решений:** автор проекта; **Утверждающие лица:** TBD.

### 1. Общие сведения
**1.1. Наименование:** автоматизированная система поддержки обработки корпоративных IT-заявок и регламентов на базе локального интеллектуального агента SADEQ UAA.  
**1.2. Основания:** [IDEA+ 0.3](01_IDEA_PLUS_REBASELINE.md); [исследование вакансий](../MARKET_DRIVEN_MVP_2026_11/README.md); PRD-001 и HLD v0.1, пересматриваемые по этому ТЗ.  
**1.3. Сроки:** TBD — календарные даты и ресурсы не утверждены. Порядок — этапы P0 и P1 с промежуточными результатами.  
**1.4. Источники финансирования:** внутренний R&D/учебный проект; утверждённый бюджет отсутствует.  
**1.5. Результат:** воспроизводимый локальный MVP, код, данные для испытаний, техническая документация, протоколы и доказательства результатов. Разработчик не заявляет промышленную готовность до испытаний.

### 2. Цели и назначение создания АС
**2.1. Назначение:** помощь оператору Service Desk в чтении регламентов, анализе обращения, подготовке ограниченного действия и проверке результата без предоставления LLM самостоятельных полномочий.  
**2.2. Измеримые цели:** (a) завершение сценария заявки через разрешённый mock ITSM; (b) воспроизводимые источники ответа; (c) отказ в запрещённом действии; (d) проверяемое состояние после операции; (e) исполненные тесты и метрики.  
**2.3. Критерий внедрения:** отсутствие незакрытых критических тестов, независимое заключение, человеческое решение о релизе. Окупаемость, ускорение работы, качество ответов и SLO определяются экспериментально.

### 3. Характеристика объекта автоматизации
**3.1. AS-IS:** пользователь получает заявки и ищет информацию в отдельных документах; ручная квалификация обращения, формирование ответа и перенос в ITSM выполняются без общего evidence trail. AS-IS является **гипотезой типичного процесса**, не результатом обследования конкретной организации.  
**3.2. TO-BE:** заявка и документ проходят контролируемый импорт; агент находит доказательства и предлагает действие; policy и человек разрешают его; система подтверждает результат и сохраняет audit.  
**3.3. Объект:** демонстрационный синтетический контур IT-службы, mock ITSM, набор локальных регламентов без реальных ПДн/секретов; промышленная интеграция — за пределами P0.  
**3.4. Условия:** Windows 11 host + Docker/WSL/local GPU as lab; окончательная контейнерная схема и модели уточняются по измерениям.

### 4. Требования к автоматизированной системе
#### 4.1. Требования к системе в целом
**4.1.1. Структура:** B01 Gateway, B02 Object/Event Core, B03 Knowledge, B04 Intelligence, B05 Policy/Action, B06 Agent Factory (P1+), B07 POLYGON, B08 Operations; допускается модульное приложение с отдельными защищёнными процессами для политики, данных и квалификации. C4 не равен числу Pod.  
**4.1.2. Режим работы:** автономный локальный контур без вызова внешних LLM API. Обязателен подтверждённый запрет egress на этапе испытаний, но загрузка официально разрешённых артефактов допускается по отдельной офлайн-процедуре.  
**4.1.3. Идентичности и права:** проверенный субъект, tenant, object ACL, роль, scope, разрешённая операция; tenant от доверенного ID контекста, не из неаутентифицированного тела сообщения.  
**4.1.4. Информация:** источники с правом использования, версии, хэши, provenance, дата источника, классификация, ограничения хранения; запрет логирования секретов.  
**4.1.5. Надёжность:** атомарная регистрация события, идемпотентность, checkpoint/recovery; RTO и RPO устанавливаются после BIA/испытаний; недостоверный статус внешнего действия `EXECUTION_UNKNOWN`.  
**4.1.6. Безопасность:** FATHER Contract-Strict — closed schema, разрешённые отправители/получатели/алгоритмы; UAG вне LLM; human approval; риск-реестр начинается с IDEA+; неавторизованное действие fail closed.  
**4.1.7. Наблюдаемость:** trace_id в запросах и событиях, latency p50/p95, TTFT, токены, GPU/VRAM, количество отказов, eval results.  
**4.1.8. Совместимость и эксплуатация:** Python 3.12 и FastAPI в качестве предполагаемой базы; PostgreSQL, Qdrant, Ollama; Neo4j в P1. Docker Compose P0, K8s P1; версии фиксируются после compatibility test.  
**4.1.9. Качество:** не гарантировать безошибочные выводы модели; required ABSTAIN/REVIEW_REQUIRED при недостатке данных, точный источник каждого существенного утверждения.  
**4.1.10. Доступность:** веб-интерфейс инженера/согласующего/экзаменатора; успешные/неуспешные решения объясняются и трассируются.

### 6. Порядок разработки АС
Проект ведётся в Git с ADR, human commits, CODEOWNERS, change request, reviewed contracts, protected release branch and signed provenance where available. Новые функции сначала фиксируются в REQ и impact/THR, затем получают API/algorithm contract и тесты, после чего код. Любая смена модели, tool, prompt, ACL, retrieval, schema — analysis and requalification.

### 7. Порядок контроля и приёмки
**7.1.** Разработчик проводит статические проверки, unit tests, integration tests, property/negative suites, performance measurement, offline egress verification. **7.2.** POLYGON как независимый участник проверяет версию кандидата, dataset hashes, результаты и выдаёт заключение `QUALIFIED/NOT_QUALIFIED` только при фактически выполненном испытании. **7.3.** Для сдачи АС заказчику порядок предварительных испытаний, опытной эксплуатации и приёмочных испытаний согласуется по ГОСТ 34.603-92. **7.4.** Запрещено принимать при нарушении tenant ACL, несанкционированном tool call, неполном audit trail, недоказанном результате или изменённом артефакте после испытаний. **7.5.** Пороговые метрики retrieval quality / latency / SLO устанавливаются на контролируемом baseline до официальной приёмки; числа без реальных испытаний не указывать.

### 8. Требования к подготовке объекта автоматизации к вводу в действие
Создать тестовый контур, пользователей и роли, fake ITSM, утвердить набор синтетических документов, настроить локальные модели и зеркало артефактов, установить deny egress, подготовить ресурсы, права, резервное копирование, планы отказов и отката; провести обучение оператора и экзаменатора на тестовых сценариях.
