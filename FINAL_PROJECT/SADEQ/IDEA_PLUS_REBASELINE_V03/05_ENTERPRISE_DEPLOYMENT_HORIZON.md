# SADEQ-DEPLOY-HORIZON-001 — Целевая корпоративная установка
**Версия:** 0.1 · **Дата:** 2026-11-27 · **Статус:** DESIGN / NOT DEPLOYED / NO CONTRACT CUSTOMER.

## 1. Организационный контур: конкретное рабочее место
**Класс организации:** крупная организация с собственной ИТ-службой и ограниченным корпоративным контуром (предприятие, больничная ИТ-инфраструктура или оператор корпоративных систем).
**Первое подразделение:** служба эксплуатации информационных систем, Service Desk (L1/L2) и инженер дежурной смены.
**Пользователь:** инженер сопровождения заявок; **согласующий:** руководитель смены или владелец сервиса; **владелец данных:** ITSM/документация; **ИБ:** Security Officer/SOC; **POLYGON:** независимый экзаменатор.
**Расположение:** внутренний серверный контур, в DMZ не размещать модель/данные; взаимодействие с корпоративным IAM, системой заявок и согласованным внутренним репозиторием регламентов через сегментированные шлюзы.
**Статус:** целевая референсная схема, без реального заказчика/адреса, не продуктовая установка.

## 2. Один бизнес-процесс
**Событие:** в ITSM появляется обращение вида `INCIDENT / REQUEST` с идентификатором, приоритетом и объектом (синтетический контур).
**Действие:** агент проверяет схему/права, создаёт или связывает объект, записывает событие, извлекает разрешённые фрагменты регламентов, объясняет вероятные действия, создаёт типизированное предложение обновления заявки.
**Согласование:** действие с последствиями требует одобрения уполномоченного лица; UAG перепроверяет action hash, объект, state version, TTL, rights.
**Результат:** запись в mock ITSM, независимая сверка состояния заявки и audit/evidence; отсутствие подтверждения → MISMATCH.
**Граница полномочий:** доступ к производственным системам, конфигурации, секретам, командам shell, больничным/пациентским сведениям и реальным данным пользователей в P0 запрещён.

## 4. Из чего состоит готовый MVP
- API: `POST /incidents`, `POST /documents`, `POST /queries`, `GET /requests/{id}`, `POST /proposals/{id}/decision`, `GET /audit/{trace_id}` — **предварительные endpoint names**, контракт v0.2 нужно спроектировать.
- Данные: PostgreSQL как authoritative objects/events/state/checkpoints, Qdrant как индекс, локальное хранилище source bytes с правами, отдельные trace/metrics.
- Model: выбрать локальную русскоязычную инструкционную модель на основе тестов; модель не имеет credentials к ITSM.
- Deployment: Docker Compose и инструкции офлайн-установки в P0; K8s/Neo4j обязательны к исследованию/приёмке OTUS P1.
- Security: tenant-safe authorization, policy before retrieval and tool, closed schemas, minimal egress and secrets masking.

## 5. Точки корпоративного включения
1. **ITSM:** API входящих заявок и mock-песочница для одобренных изменений, далее интеграционный контракт под реальный продукт.
2. **Документооборот:** read-only approved регламенты через импорт и реестр версий, никакого самовольного индексирования «всего диска».
3. **Корпоративный IAM:** референсный маппинг user/role/tenant, применение прод-AD/LDAP/OIDC только по документированному контракту.
4. **Мониторинг/SOC:** метрики и редактированный аудит без секретов.
5. **Change Management:** изменение действия/модели/политики требует review, POLYGON, human signoff.

## 6. Модель целевого развертывания
- **LAB:** локальная Win11 / WSL2/Docker, RTX3060 12GB, RAM32GB, искусственные данные — единственный утверждаемый P0 объект реализации.
- **PILOT:** изолированная корпоративная песочница на сервере/внутреннем сегменте после P0 квалификации; параметры и заказчик TBD, доступ только к тестовой ITSM.
- **PRODUCTION:** отдельное будущее решение по информационной безопасности, BIA, SLA, мощности, защите данных, документам и договорной приёмке. **Не утверждён и не развёрнут.**

## 7. Системные риски
Утечка между арендаторами, prompt injection через документы, replay/duplicate tool call, нарушение согласования, недостоверная рекомендация и взрыв расходов по GPU. Каждая угроза вносится в живую матрицу с IDEA+, review at each gate; никаких решений о снятии риска без выполненных тестов.
