# Semantic Caching для LLM

Семантический кеш ищет не точное совпадение строки, а близкий по смыслу запрос. Запрос преобразуется в embedding, затем выполняется векторный поиск по ранее сохранённым запросам и ответам.

## Путь запроса

1. Нормализовать запрос и определить tenant/user scope.
2. Добавить безопасный контекст: версию prompt, модель, политику, язык и допустимую часть истории диалога.
3. Построить embedding.
4. Найти ближайшие записи в vector store.
5. Проверить similarity threshold, TTL, freshness и policy version.
6. При HIT вернуть ответ после проверки безопасности.
7. При MISS вызвать LLM, проверить ответ и сохранить допустимый результат.

## Почему контекст обязателен

Одинаковая короткая фраза может иметь разный смысл в разных диалогах. Поэтому ключ должен учитывать не только последний запрос, но и релевантную часть окна контекста. Иначе кеш может вернуть семантически похожий, но фактически неправильный ответ.

## Настраиваемые параметры

| Параметр | Эффект при увеличении | Риск |
|---|---|---|
| similarity threshold | выше точность HIT | больше MISS и затрат |
| TTL | дольше переиспользование | устаревшие ответы |
| top-k | больше кандидатов | рост latency и ложных совпадений |
| context depth | выше контекстная точность | больше embedding cost |
| max cache size | больше покрытие | стоимость хранения и поиска |

## Метрики

- cache hit rate;
- false-hit rate по контрольной выборке;
- p50/p95 cache lookup latency;
- saved tokens и saved cost;
- freshness violations;
- cache size и eviction rate;
- доля ответов, заблокированных policy validation.

## Безопасность

- изоляция tenant и пользователя;
- запрет кеширования секретов и чувствительных данных;
- версия модели, prompt и safety policy входит в ключ;
- TTL и принудительная инвалидация;
- проверка cached response теми же output controls, что и нового ответа;
- аудит причины HIT/MISS без записи лишних персональных данных.

## Практический эксперимент

Прогнать набор повторяющихся и перефразированных запросов при нескольких threshold. Для каждого варианта измерить hit rate, false-hit rate, p95 latency и cost/request. Выбирать threshold по допустимому уровню ошибочных попаданий, а не только по максимальной экономии.
