## Словарь

| Термин | Простое объяснение | Архитектурное значение |
|---|---|---|
| HA / High Availability | система продолжает работать при части отказов | нет единой критической точки отказа |
| DR / Disaster Recovery | восстановление после крупной аварии | отдельная площадка и проверенный план восстановления |
| Failover | переключение на резерв | health + fencing + переключение маршрута |
| Replication | копирование изменений на резервную БД | режим синхронизации влияет на задержку и риск потери данных |
| Backup | независимая точка восстановления | не заменяется репликой и должна регулярно проверяться |
| RTO | максимальная допустимая длительность восстановления | время от отказа до восстановления сервиса |
| RPO | максимально допустимая потеря данных во времени | насколько старую точку восстановления можно принять |
| Split brain | две копии одновременно считают себя главными | риск конфликтующих записей, нужен fencing/consensus |

## 1. Бизнес-цель и NFR

Для FATHER AI-сервиса отдельные workload classes:
- A: критические API с жёстким SLO на ответ и маршрутизацию; сохранять idempotency и audit.
- B: модельный inference — допускает очередь/деградацию; свои SLI: TTFT, tokens/s, completion latency.
- C: асинхронная обработка документов / RAG / батчи — можно восстанавливать из надёжного журнала задач.

**Числовые RTO/RPO должны быть согласованы с заказчиком**, а не выдуманы архитектором. Пример сценариев для обсуждения (не принятые требования):
- Tier A: RTO 5 минут, RPO 0–1 минута.
- Tier B: RTO 30 минут, RPO 5 минут.
- Tier C: RTO 4 часа, RPO 1 час.

Это **иллюстративные значения**, а не характеристики работающей системы.

## 2. Логическая схема

```text
Users / Clients
       |
Traffic Manager (health checked, failover policy)
       |
    +--+-------------------------------+
    |                                  |
 DC-A / primary                    DC-B / standby
 LB / ingress                      LB / ingress
 stateless API pods                stateless API pods (warm)
 UAG + policy                      UAG + policy
 inference pool                    inference pool / fallback
 worker fleet                      worker fleet
    |                                  |
 PostgreSQL primary --- WAL replication ---> standby
    |                                  |
 event outbox + durable queue      durable queue / replay
    |                                  |
 independent encrypted backups -> separate backup store
                       |
        restore tested, not assumed
```

**Границы:** отказ AZ/узла ≠ отказ всего DC; реплика БД ≠ backup; active-active для записей сложнее active-passive и требует отдельного ADR.

## 3. Варианты для заказчика

| Вариант | Когда разумен | Преимущества | Цена и риск |
|---|---|---|---|
| A. Single-DC Multi-AZ + backups | Требования ограничены отказом узла/зоны | Проще, дешевле | Не покрывает потерю региона/ДЦ |
| B. Active-passive два ДЦ | Нужно DR и контролируемый failover | Меньше конфликтов записи | Standby capacity, переключение, RPO |
| C. Active-active два ДЦ | Требуется продолжать выдачу в обоих ДЦ | Потенциально выше доступность | Дорогая согласованность, конфликты, маршрутизация, latency |

**Предварительно предлагается B для исследовательского дизайна**, но итоговый выбор только после RTO/RPO, допустимого бюджетного лимита, topology, network delays и рисков.

## 4. Как считать RTO/RPO

```text
RTO_observed = t(service_healthy_again) - t(fault_detected)
RPO_observed = t(last_committed_before_fault) - t(last_recovered_commit)
```

При реальном тесте отдельно фиксируются время возникновения отказа, обнаружения и восстановление user-facing SLO, чтобы измерение только от обнаружения не скрывало задержку мониторинга.

- Синхронная репликация: меньший риск потерь при подтверждённой записи, но задержка сети и зависимость доступности записи от подтверждений.
- Асинхронная репликация: меньше задержка, но lag может увеличить RPO.
- Backup: отдельный ключ доступа, шифрование, retention, immutability, регулярное восстановление.
- При failover БД требуется защита от split brain, fencing и единый источник лидерства.

## 5. Сценарии отказов

| Fault injection | Что ждём | Как подтвердить |
|---|---|---|
| Убит один API pod | Запросы идут в другую реплику | latency/error rate + trace |
| Потеря ноды inference | Удаление из балансировки, queue/fallback | timeouts и rate of success |
| Пропала primary DB | Обоснованное promotion standby, без двойной записи | журнал failover + tests |
| Отказ DC-A | Traffic Manager переводит на DC-B | end-to-end synthetic checks |
| Потеря одного event consumer | no data loss, controlled redelivery | replay/idempotency evidence |
| Шифрование/удаление рабочих данных | restore из изолированного backup | restored data verification |
| Сбой при DR | запрет silent PASS, rollback/stop | incident report + runbook |
