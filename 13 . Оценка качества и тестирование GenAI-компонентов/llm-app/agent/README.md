# Agent Demo

Папка с controlled-agent сценарием поверх того же локального RAG.

Все команды ниже предполагают запуск из корня репозитория.

## Что показываем

Сценарий: агент проверки кредитной заявки по внутренним политикам `North Star Credit`.

Пример вопроса:

```text
Проверь кейс C-102: может ли клиент подать заявку сейчас, будет ли автоотказ
или ручная проверка, какие документы нужны, какой диапазон ставки возможен,
сколько живёт оферта и можно ли потом сделать частичное досрочное погашение?
```

Почему этот сценарий подходит:

- вопрос естественно распадается на 5-6 policy-блоков;
- факты лежат в разных чанках, поэтому retrieval хорошо виден;
- легко показать самокоррекцию, если в кейсе есть конфликт или пробел в данных.

## Что лежит здесь

- `run_agent_credit_demo.py` — entrypoint controlled-agent demo
- `data/mock_credit_cases.json` — mock tool-данные по кейсам

Фактические policy-знания агент берёт из общего RAG-слоя в `rag/data/credit_policy_chunks.json`.

Mock tool сейчас один:

```text
get_mock_application(case_id)
```

Он отдаёт карточку клиента и пишет вызов вместе с результатом в обычные логи.

## Как запускать

Нужно только локальное окружение:

1. `Qdrant`
2. `Ollama`
3. локальные модели:
   - `hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M`
   - `nomic-embed-text`

Команды подготовки:

```bash
docker compose up -d qdrant
ollama serve
ollama pull hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M
ollama pull nomic-embed-text
```

Первый запуск с переиндексацией:

```bash
./.venv/bin/python -m agent.run_agent_credit_demo --reindex --case-id C-102
```

Одноразовый прогон:

```bash
./.venv/bin/python -m agent.run_agent_credit_demo \
  --case-id C-102 \
  --question "Проверь кейс: может ли клиент подать заявку сейчас, нужны ли допдокументы, какая ставка возможна и можно ли сделать частичное досрочное погашение?"
```

Показать все mock-кейсы:

```bash
./.venv/bin/python -m agent.run_agent_credit_demo --list-cases
```

В интерактивном режиме доступны:

- `:cases`
- `:case`
- `:use C-103`
- `:help`
- `exit`

Для этого demo не нужен `Langfuse`: агент пишет весь свой trace в стандартный лог.

## Что логируем

Вместо `Langfuse` агент пишет свой путь в обычные логи:

- исходный запрос;
- отдельные крупные блоки `AGENT REQUEST`, `CONTEXT LOAD`, `PLAN BUILD`, `PLAN EXECUTION`, `SELF-CHECK`, `REVISION`, `RESULT EVALUATION`;
- план и список подзадач;
- вызовы mock tool;
- какие policy-чанки были подняты для каждой подзадачи;
- черновые выводы;
- замечания self-check узла;
- что агент исправил перед финальным ответом.

Важно: в логи идёт объяснимый trace шагов, а не сырой скрытый chain-of-thought.

Дополнительно trace теперь размечен циклами:

- `cycle=1` — исходный план, проход по шагам и первая оценка;
- `cycle=2` и далее — адресная коррекция после self-check;
- в конце отдельно печатается `RESULT EVALUATION` с числом проверок, статусами и итоговой сводкой.

## Схема шагов

```text
user question
  -> planner
  -> mock case tool
  -> subquestion retrieval
  -> draft answer
  -> self-check
  -> optional revision
  -> final answer
```

## Возможные шаги агента

1. Выделить intent и обязательные части вопроса.
2. Загрузить кейс клиента через `get_mock_application(case_id)`.
3. Разбить задачу на подзапросы:
   - eligibility
   - auto-decline
   - manual review
   - documents
   - pricing
   - offer validity
   - early repayment
4. Для каждого подзапроса выполнить retrieval в `Qdrant`.
5. Собрать структурированные факты вида `claim + source_chunk_ids`.
6. Сгенерировать черновой ответ.
7. Проверить ответ на полноту, конфликты и unsupported claims.
8. При необходимости перезапросить только проблемный блок.
9. Вернуть финальный ответ с источниками и явными оговорками.

## Как агент строит план

Планировщик не пытается сразу отвечать. Он сначала делает компактный структурированный план:

- `goal`: что именно просит пользователь;
- `required_checks`: какие policy-проверки обязательны;
- `missing_case_fields`: каких данных о клиенте не хватает;
- `subquestions`: короткие подзапросы для retrieval;
- `answer_sections`: из каких блоков должен состоять финальный ответ.

Пример:

```json
{
  "goal": "Проверить возможность подачи заявки и условия по кейсу C-102",
  "required_checks": [
    "eligibility",
    "auto_decline",
    "manual_review",
    "documents",
    "pricing",
    "offer_validity",
    "early_repayment"
  ],
  "missing_case_fields": ["internal_rating"],
  "subquestions": [
    {
      "check_id": "eligibility",
      "question": "Может ли клиент подать заявку сейчас после прошлого отказа?"
    },
    {
      "check_id": "auto_decline",
      "question": "Есть ли условия для автоотказа по PTI и просрочке?"
    },
    {
      "check_id": "manual_review",
      "question": "Нужна ли ручная проверка?"
    },
    {
      "check_id": "documents",
      "question": "Какие документы нужны на сумму 350000?"
    }
  ],
  "answer_sections": [
    "Допуск к заявке",
    "Автоотказ",
    "Ручная проверка",
    "Документы",
    "Ставка и срок",
    "Срок жизни оферты",
    "Досрочное погашение"
  ]
}
```

## Как выглядит самокоррекция

Self-check узел не переписывает всё подряд. Он проверяет три вещи:

- покрыты ли все части вопроса;
- есть ли выводы без источника;
- не сказал ли агент слишком уверенно там, где данных не хватает.

Типичный пример:

- draft: "Клиент может подать заявку сейчас."
- critic: "В кейсе прошлый отказ был 10 дней назад, а политика требует ждать 14 дней."
- revision: "Сейчас подать повторную заявку нельзя; нужно дождаться 14 календарных дней после отказа."

## Что возвращает mock tool

`get_mock_application(case_id)` возвращает:

- возраст;
- доход;
- стаж;
- PTI;
- зарплатный ли клиент;
- сумму и срок кредита;
- просрочки;
- дату прошлого отказа;
- признаки нестандартного дохода или fraud flags.

Этого хватает, чтобы показать и декомпозицию, и самокоррекцию.

## Подходит ли Qwen3-4B

Да, `Qwen3-4B` годится для этого demo, если держать задачу в узких рамках:

- низкая температура;
- короткие structured prompts;
- JSON-план вместо свободных рассуждений;
- ограниченное число шагов;
- отдельный self-check узел;
- retrieval как источник фактов, а не память модели.

Где `4B` уже слабее:

- свободный tool-using без жёсткой схемы;
- длинные многоходовые сценарии с 10+ ветками;
- ситуации, где нужно тонко удерживать много исключений одновременно.

Практический вывод: для demo controlled-agent поверх RAG модель подходит. Для более свободного универсального агента лучше будет `Qwen3-8B`.
